## Search evidence and limits

`SearchResponse` contains `phones: Phone[]`, parallel `evidence` entries keyed by exact model name, provider `sources`, `requestedCount:20`, `status`, `message` and `constraintsRelaxed:false`. Evidence holds currency (null when price is unknown), notes, per-field sources, unknown fields, and exact-model image metadata when available. Known prices use the explicitly requested ISO currency; null price has no asserted currency. Country/currency alone never imply a price, stock or new-condition requirement; filters and displayed prices must use that same currency. No implicit exchange conversion occurs.

Every admitted phone must have sourced identity. For broad research, local price may be unknown: return price:null, evidence.currency:null, no price citation, and include price in unknownFields. Never replace unknown price with zero or a model estimate. An explicit budget, price request, new-only request, confirmed local-stock constraint or adjusted price filter requires a sourced known local price. Explicitly required specifications must be known and sourced; all other unsupported specification leaves become null, never zero or false. Known numeric values must be finite/nonnegative, with positive size/battery/refresh values. Every retained field needs a citation to a URL in the provider's actual grounding metadata, or its explicitly resolved destination, whose actual page title or single JSON-LD Product name identifies the exact phone. Mixed Product records are rejected. Fetched Product offers and descriptions are supplied to extraction; pre-owned/refurbished/used price evidence stays explicit, and new-only requests require an explicitly new price source. Official hosts can establish a manufacturer omitted in their own page titles. Google grounding titles often contain only domains; those are not treated as exact-model titles. Fabricated URLs, wrong-model titles, currency mismatches, duplicate normalized names (including storage/color variants) and failures of Sparta's `applyFilters` are discarded. Extracted measurable budgets, brands, series, release years and latest-generation exclusions are checked server-side. Subjective feature/use-case reasoning and constraint extraction remain model-assisted; evidence and notes stay visible for review. No `verified` label is fabricated: source metadata proves retrieval, not independent physical testing or source correctness.

`complete` means at least 20 admitted distinct models. `shortage` means fewer than 20, discovery reported evidence of a shortage, all names survived validation, and all spec batches succeeded. `partial` means some admitted models but incomplete research or rejected candidates. `unverified` means no candidate passed; it does **not** mean no matching phone exists. These statuses never trigger constraint relaxation. This is a bounded research attempt, not an exhaustive database or a guarantee that a broad live query will return 20. Live acceptance must demonstrate 20 actual grounded models before claiming that requirement fulfilled.

## Configuration and boundaries

- `GEMINI_API_KEY` is read only by server code and is never returned, logged or committed. Missing configuration yields 503. No `NEXT_PUBLIC` key or source Vite key exposure is copied.
- Optional server-only `GEMINI_MODEL` and `GEMINI_LIVE_MODEL` select deployed models. Defaults are stable `gemini-3.8-flash` and `gemini-3.8-live`, confirmed in the configured credential's actual model catalog. There is no automatic legacy-model fallback. The SDK is initialized lazily with `v1beta`; Live token and browser connection must use the same API version.
- Strict Zod input schemas reject unknown properties; maximum 60 phones, 30 chat messages, 100 local reviews, 4,000 characters per main text field and approximately 2 MiB decoded audio. JSON bodies are byte-counted while streaming, capped at 3.2 MB; declared content length cannot bypass the cap.
- Same-origin/Fetch Metadata checks reject cross-site browser calls. Public Host and forwarded protocol establish the browser origin because Next can construct an internal request URL using its bind hostname. This public app has no account authentication; scripts can call the public routes. Product-page fetches use fixed trusted-host allowlists, HTTPS only, no credentials/custom ports, manual redirects (maximum three hops), a 1 MB streaming HTML limit and 3-second timeout. Google grounding redirect URLs are allowed only on their specific path and can land only on allowlisted product-page hosts. Image CDN hosts are separately allowlisted; HTML is parsed for titles, Open Graph metadata and JSON-LD Product data using JSON.parse, never executed. Reading includes the bounded body because some retailers place Product offers after the head. SLOT product images use its separately allowlisted api-prod.slot.ng CDN. Public source links require HTTPS hostnames with no credentials, IP literals or local hostnames.
- Process-wide budget: 30 requests/minute, at most 3 live tokens/minute, at most 4 active requests. All callers share the cap; no user-controlled IP header can evade it. **Process-local ceiling:** multiple replicas/restarts reset or multiply limits. Use shared rate storage/platform quota before scaling; these are not per-user account quotas.
- Overall deadline 230 seconds / route maximum 240 seconds, SDK request timeout 80 seconds, one SDK attempt (no hidden retries), bounded output tokens. Flash requests use `thinkingLevel: LOW`, including discovery and extraction; explicit deep chat uses HIGH. Numeric thinking budgets and unsupported MINIMAL are not used. Safe server diagnostics record only fixed stage names, finish reason and token counts. Up to four one-phone research/extraction jobs run concurrently; each resolves source pages in groups of four (at most 32 source pages per batch). Disconnect/deadline signals reach SDK calls and product fetches; HTTP returns on cancellation even if a provider stalls. Cancelling local work does not guarantee Google cancels already-billed service execution.
- Upstream errors/validation internals never leak provider bodies or keys. Safe status-based messages distinguish quota/rate limits, rejected credentials, unavailable models, unsupported configurations, timeout, and generic service failure. All JSON responses have `Cache-Control:no-store`.
